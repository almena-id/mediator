# almena-mediator — notes for contributors and agents

Server of Almena ID, a decentralised messaging platform based on DIDComm Messaging v2.0
(https://identity.foundation/didcomm-messaging/spec/v2.0/). DIDs follow W3C DID (https://www.w3.org/TR/did/). Phases 1–8 of SPEC.md (Appendix I) are done: the DIDComm library, the mediator skeleton, mediation, live delivery / invitations / federation, push wake-ups, hardening, and the administration (onboarding, public and private mediators, the portal). Calls (TURN credentials, call rings, phase 6) were removed on 2026-11-10.

This project is independent: it has its own Docker Compose file, env file and tooling.
It shares nothing with `../wallet` except the protocol; the wallet depends on the `almena-didcomm` crate as a git dependency pinned to a commit, so a library change reaches it only when its pin moves (see SPEC.md, Appendix B).

## Layout

Cargo workspace:

- `crates/didcomm/` — `almena-didcomm`: DIDComm v2.0 library (keys, JWS, JWE anoncrypt/authcrypt, messages, pack/unpack, `did:key`/`did:peer` resolution, walking a `did:webvh` log, possession proofs). No HTTP or storage. `route` wraps at most `MAX_ROUTING_HOPS` (4) hops, none twice.
  - `tests/spec/appendix.json` — the spec's Appendix A–C test vectors (errata noted in the file).
  - `tests/webvh/registry-did.jsonl` — a `did:webvh` log the registry (`../api`) wrote; the wallet's resolver is tested with the same one.
  - `tests/registry/notice.json` — a holder notice the registry (`../api`, `registry_api.didcomm`) packed: a `forward` to the mediator around an authcrypt message to a `did:peer:2`; `tests/registry_notice.rs` unpacks it as the mediator and the wallet would. The API writes it again with `uv run python -m tests.notice_fixture`.
- `crates/interop/` — `almena-interop`, tests only: `almena-didcomm` and the mediator against didcomm-rust (SICPA) and Affinidi's DIDComm library, both ways. Nothing else depends on it.
- `interop/veramo/` — a Veramo client run against a live mediator (`node check.ts`); Veramo does not conform yet, see SPEC.md §10.
- `crates/mediator/` — `almena-mediator`: the service.
  - `admin.rs`: the administration's own SQLite (`ALMENA_ADMIN_DB_PATH`), apart from the messages: the site once set up (public URL and mode; the mode is fixed for good, the URL moves with `move_site`, which turns every administrator into an invitation at the new address), the domain being proven, the setup code's hash, the administrators. `setup.rs`: the onboarding (the setup code always in a form's body, never in a URL; `GET /setup` asks for it, `POST /setup` takes it, in the onboarding and in the portal alike), a router served alone until the mediator is set up (`main.rs` then starts the full one on the same port): the setup code from the log or `almena-mediator setup`, the URL and the mode, the proof (the value is `AdminStore::proof_value`: HMAC of the host under `proof_secret`, the same for a domain at this mediator however often it is asked; TXT at `_almena-mediator.<host>` — asked of the zone's authoritative name servers first, then public resolvers, then the system's, none cached, because a local resolver keeps a negative answer for the zone's negative TTL; `a_published_record_is_found_past_any_cache` tries it against the real DNS —, HTTPS at `/.well-known/almena-setup`, through `transport::PublicOnlyResolver` unless `ALMENA_OUTBOUND_ALLOW_INSECURE`; name servers are asked only at public addresses). `ALMENA_PUBLIC_URL` (with `ALMENA_ACCESS`) skips it. `signin.rs`: signing in with the Almena wallet, as the registry's portals do (SIOPv2 `direct_post`): requests held in this process for 5 minutes, at most `PER_CLIENT` (5) from one client (`routes::Client`, as the rate limit counts it), the `id_token` checked (EdDSA by the `did:key` that is its `iss` and `sub`, `aud` the public URL, the nonce, `iat`); the wallet derives that key from the mediator's origin, so an administrator is one DID here and nowhere else. `portal/`: `mod.rs` — `/setup` with the code makes the first administrator (whoever answers first; the code goes with it) — the onboarding's last page waits for the full mediator on `/health` and posts the code there by itself —; every wallet QR page renews its request every `signin::RENEW_SECS` (60) through `/portal/sign-in/renew` until a wallet reads it (`SignIns::renew`), `/portal` signs administrators in; `dashboard.rs` — the dashboard's sections under one navigation: overview (`Store::totals`), mailboxes (`Store::mailboxes`, searched, paged, removable), members (private only), administrators, and the invitation handlers; `site.rs` — the site page and moving the URL (proof as at setup, then `AppState::restart` makes `main.rs` re-exec itself as the new `did:web` — on Windows run itself as a child and wait for it; `ALMENA_PUBLIC_URL` pins it). Until there is an administrator, `/` redirects to `/setup`. Sessions are a cookie (`almena_admin`, HttpOnly, SameSite=Strict, Secure under HTTPS) whose hash `admin.rs` keeps, 12 h idle; the waiting browser collects the answer with its own cookie (`almena_signin`). Invitations (`admin.rs`: `invitations`, `members`): an administrator's (one use, 7 days, taken at `/portal/join/{id}` by signing in) and a private mediator's member invitations (uses, days, a label): the mediator's own Out-of-Band invitation with the invitation's id (`oob::member_invitation`), which the wallet sends back as the `pthid` of its `mediate-request` (it already does); `dispatch/mediation.rs` takes one use for a new mediation (given back if the mediator is full) and records the member, a mediation already held needs none. Removing a member deletes its mailbox (`Store::remove_mediation`). The DID limit per mailbox (`ALMENA_MAX_RECIPIENT_DIDS`, 1000) goes to the wallet in `mediate-grant` (`max_recipient_dids`) and a refused `add` over it says `reason: "limit"` (`dispatch/mediation.rs`, Almena extensions); one `recipient-update` carries at most `MAX_PROVED_ADDS` (100) proved `add`s — a cap per message, not the mailbox's — and `MAX_UPDATES` (1000) entries; `messages-received` at most `MAX_ACKNOWLEDGED` (1000) ids (`pickup.rs`). A `mediate-request` is granted under `Mediator::granting`, so a wallet asking twice at once spends one invitation use. The first administrator is made by `AdminStore::claim` (count and code checked in the same transaction), and a move from the portal writes no setup code to the log (`main.rs`): the administrators were invited again. A private mediator's home and `/oob` pages offer no invitation of their own; `/oob` opens the one it is given. `examples/smoke.rs` takes an invitation link after the URL.
  - `config` reads `ALMENA_*` env vars; `identity` holds the mediator's `did:web`, keys (`ALMENA_KEYS_PATH`) and DID document.
  - `store/`: the `Store` trait, implemented on SQLite (`sqlite.rs`, `rusqlite` with SQLite bundled; `ALMENA_DB_PATH`, `:memory:` for tests and `task dev:memory`), and its contract test. Redis was removed on 2026-11-10: the mediator runs as one instance.
  - `dispatch/`: unpacks what reaches `/didcomm` or `/ws` and dispatches — `protocols.rs` (Trust Ping, Discover Features — `matches` is linear however many `*`, at most 32 queries —, problem reports), `mediation.rs` (Coordinate Mediation, `forward`), `pickup.rs` (Message Pickup), `live.rs` (live-delivery sessions, held in this process), `relay.rs` (forwarding to other mediators: stored, then sent by a background worker), `devices.rs` (push protocols: device registration).
  - `push/`: wake-ups through FCM (`fcm.rs`) and APNs (`apns.rs`), coalescing, the `Pusher` trait.
  - `transport.rs`: outbound HTTPS with the SSRF guard, and the `did:web` / `did:webvh` resolver. `oob.rs`: the Out-of-Band invitation.
  - `routes` is the axum router: HTTP and WebSocket endpoints, rate limit, HTTP status mapping.
  - `home.rs`: the page at `/` (the status, version and DID `/health` also gives, the invitation QR and its `almena://` link); the icon (`crates/mediator/assets/icon.png`, compiled in) is the favicon. Its `layout` wraps every browser page (also `/oob`) in the header and footer of Almena's portals (catalog, registry, status) and their typefaces: Chakra Petch (brand, headings), Inter (text), JetBrains Mono (values), compiled in from `crates/mediator/assets/fonts` (SIL OFL, licences beside them) and served at `/fonts/{name}`, so a page never calls a third party.
  - `capacity.rs`: samples the mediations held every 5 s, for `/health` and the metrics (SPEC.md §11). The mediation ceiling is checked in the store when granting, the WebSocket one in `routes`.
  - `metrics.rs`: Prometheus counters, served by their own listener (`ALMENA_METRICS_ADDR`), not by the router.
  - `src/main.rs`: logging, start-up (the site, then the onboarding or the mediator), graceful shutdown, the `healthcheck`, `setup` and `rotate-keys` subcommands. `testing.rs` has a test mediator and wallets.
  - `examples/smoke.rs`: end-to-end client against a running mediator (`task smoke`).
- `Dockerfile`, `compose.yml` (the mediator alone), `.env.example` — container build and local run. No proxy, TLS or DNS provider here (no Caddy, no Cloudflare): what goes in front is whoever runs it's decision — locally `../develop`'s Caddy. The public URL and the mode are never in `.env`: the onboarding sets them (`ALMENA_PUBLIC_URL` stays as a development and test shortcut, set by `task dev`). `data/` (local keys and databases) is git-ignored.
- `SPEC.md` — the Almena Mediator specification: the DIDComm v2.0 profile, deviations and Almena's own extensions, with their sources; its appendices hold the design (decisions, code layout, storage, scaling, metrics, phases). Read it before DIDComm work and keep it current.

## Rules

- Magenta `#d63384` is the mediator's identity and the colour `assets/icon.png` is drawn in: `--brand` in `home.rs` (`LAYOUT_CSS`), carried by the mark in the header and footer and the "Open in Almena wallet" button. Green and red carry the status only.

- Everything is written in English.
- `almena-didcomm` denies `unwrap`/`expect` outside tests (`clippy.toml` allows them in tests) and uses `thiserror`; the mediator binary uses `anyhow`.
- Every HTTP endpoint of the public router is declared with `#[utoipa::path]` and registered through `OpenApiRouter` in `crates/mediator/src/routes.rs`, so it appears in `/openapi.json` and `/docs`. Keep the README endpoint table in sync.
- Tasks live in `Taskfile.yml` (`task --list`). Before finishing a change: `task check` (fmt check, clippy -D warnings, tests).
